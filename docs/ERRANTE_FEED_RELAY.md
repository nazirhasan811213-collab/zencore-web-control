# ZenCore to Errante live feed relay

The original `/webhook` runs the existing TradingView ingress validation, strips `authToken`, immediately starts a separate HTTPS POST to the pinned Errante `/relay/webhook`, and continues the existing local webhook processing without awaiting Errante. No changes to trading decisions, risk rules or existing TradingView alerts are required.

Receiver: set `ZENCORE_RELAY_RECEIVE_ENABLED=true` and a dedicated `ZENCORE_RELAY_SECRET`. Sender: set the same dedicated relay secret plus `ZENCORE_RELAY_TARGET_URL=https://zencore-errante.onrender.com/relay/webhook`. These values are set directly in the two existing Render services. Do not copy database, login, webhook, Telegram or trading credentials. Errante bootstrap always clears its outgoing relay URL to prevent loops.

Each message is authenticated with HMAC-SHA256 over send time, random ID and exact sanitized body. Receiver preserves the original `emittedAt`, entry identity and timeframe, rejects data older than 30 seconds, rejects duplicate IDs, and routes through the same internal webhook parser. Existing direct-webhook authentication settings are preserved on both installations; the relay always requires its own HMAC secret even when the source still uses legacy ingress validation.

Delivery is immediate and bounded to four concurrent requests, a 2.5-second total deadline and a keep-alive agent. There is no delayed replay queue or heartbeat generator. A slow, sleeping or failed Errante cannot delay the original webhook response or block original execution. Dropped messages are reported; later real feed events can recover the display, but missing execution events are never manufactured. This is best-effort live fan-out, not guaranteed delivery. Do not enable Errante execution until real feed completeness and demo orders are verified.

`/ready` exposes non-secret `relay` counters and timestamps. Sender `lastRoundTripMs` includes receiver processing and return network time; it is not one-way latency. Receiver `lastReceiveAgeMs` measures source emit to receipt (including TradingView delivery and relay); `lastAppliedSourceAgeMs` includes internal processing. Failed requests, dropped requests and successful applications are separate counters. A new deployment resets these in-memory counters. Relay health does not change original readiness.

No zero-delay guarantee is possible. No plan changes, new services or artificial keep-alive calls are introduced. Existing Free Errante sleep behavior remains; the first real payload after idle can time out while the receiver wakes. Live metrics and actual traffic must be checked after deploy. The destination receives the same source market data; its own database, users, Telegram and orders remain isolated.
